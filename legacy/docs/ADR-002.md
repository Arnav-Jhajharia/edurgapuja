# ADR-002 — Backend Stack

**Status.** Accepted.
**Depends on.** ADR-001 (gate offline validation) — unresolved. The pass representation below assumes offline signature verification and must be revisited if ADR-001 goes the other way.

---

## Context

The requirement set has been narrowed to twenty functional requirements covering the path from booking to gate. FR-01 to FR-13 are served by the Flutter client and the gate device. FR-14 to FR-20 are committee and platform configuration, with no product surface of their own.

Four properties constrain the choice. The capacity invariant must hold under concurrent booking during short bursts. Gate validation must answer fast and enforce single use. The payment-to-issuance transition must never retain money without issuing a pass. Background work is required for hold expiry, slot cut-off, offline reconciliation and refund retries.

Traffic is near-flat for months, then extreme for a few days.

---

## Decision

**Backend.** Django 5 with Django REST Framework.

**Database.** Postgres 16, single datastore. The capacity hold is a row with an expiry, taken under `select_for_update` inside `transaction.atomic`. Idempotency keys for payment webhooks are a unique index. No second source of truth for capacity.

**Background work.** Celery with beat for hold expiry, slot cut-off, refund retries and offline reconciliation. Broker choice deferred — Redis is conventional, a Postgres-backed queue keeps the single-datastore property. Open.

**Admin surface.** Django Admin, with two roles:

- *Committee Admin* — scoped to a single pandal. Sees and edits only its own slots, passes, occupancy and entry logs. Enforced by queryset filtering on the admin classes, not by permissions alone, since permissions do not scope rows.
- *Superadmin* — global. Onboards committees, creates the first Committee Admin account for each, and manages master data (pass types, slot types, cancellation and refund rules).

This covers FR-14 through FR-20 as configuration rather than code.

**Client contract.** drf-spectacular emits OpenAPI from the DRF serializers. openapi-generator produces the Dart client consumed by the Flutter app. Schema accuracy is enforced by annotation discipline and a CI check, since an inaccurate schema silently produces a wrong client.

**Mobile.** Flutter, for both the visitor app and the gate app.

**Auth.** OTP-based login with no password. JWT with refresh tokens via `djangorestframework-simplejwt`.

**Pass representation.** A signed token — Ed25519 via PyNaCl — over pass id, pandal, slot window and issue time, so a gate device can verify authenticity without a round trip. Consumption remains server-authoritative, enforced locally when offline and reconciled on reconnect. Authenticity and consumption are separate concerns and are kept separate.

**Testing.** pytest with pytest-django against a real Postgres. Concurrency behaviour is not observable against a mock. Hypothesis for property tests on the capacity invariant.

**Deployment.** Single container plus managed Postgres. pgBouncer in transaction mode if connection count becomes real.

---

## Consequences

**Accepted costs.** Type guarantees under mypy are weaker than TypeScript strict. Two languages rather than one, so a contract change means regenerating a Dart client from a Python-derived schema rather than flowing from a single definition. Django Admin looks like Django Admin, which suits committee volunteers and does not suit a client demo without theming.

**Rejected alternative.** A TypeScript monorepo on Next.js 15 with Prisma and Zod contracts. This was the earlier recommendation and was correct while sponsor portals, campaign management and analytics dashboards were in scope. With those removed, the remaining web surface is configuration, which Django Admin provides for free.

**Reversal condition.** If the admin portal requires a designed interface rather than a functional one, or if sponsor and analytics scope returns, the TypeScript path becomes the better base and this decision should be revisited before further investment.
