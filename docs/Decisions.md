# eDurgaPuja — Decisions

Answers from the client, recorded against the contradictions they resolve.
Each entry says what was decided, what it kills, and what it now forces.

Answered **9 September 2026**. Numbering follows `eDurgaPuja-Contradictions.pdf`.

---

## D1 · The entry credential is a one-time code, not a pass QR — *resolves C1*

> "QR code is a code to enter once generated at the gate. If not used within 3 mins, it can be generated again."

**Decided.** The pass is durable and authorises. The entry code is ephemeral and admits.
They are two different objects with two different lifetimes.

- A code is generated by the holder at the gate, admits once, and dies after three minutes.
- An unused expired code can be replaced, without limit.
- Generating a replacement must invalidate any earlier live code for that pandal on that
  pass, or two admitting codes exist at once.

**Killed:** the client document's downloadable, shareable pass QR, and its pass statuses
*Active / Used / Cancelled / Expired / Blocked* as a description of the admission artefact.
Those statuses now belong to the **pass**; the **code** has only *live / used / expired*.

## D2 · Capacity is a number each pandal sets — *resolves C2*

> "Capacity — something each puja will define. Only those number of passes will be issued for that puja."

**Decided.** The pandal holds the count. At most that many passes exist for that pandal.
Configuration rows carry price, dates and times; the pandal total is the binding ceiling.

**Consequence.** A City Pass covering six pandals must draw one from each of those six
pandals' counts, otherwise the number is not a cap at all. *Confirm — see Q3.*

---

## D3 · A City Pass has a date and no time — *resolves C3*

> "City pass — will have a date but not time."

**Decided.** The holder picks a date. There is no time slot, and the covered pandals are
visited in any order on that date.

**Killed:** the prototype screen that sells a City Pass with no date at all, and the one
that gives every covered pandal its own time slot.

---

## D4 · Product, then category — *resolves C4 and C5*

> "1) individual. Under individual there can be A) sponsor B) VIP C) para pass D) senior citizen E) donor F) anything else the pandal wants to define
> 2) group pass. This is to buy for more than one individual, say a family. Can select no of people. It's basically an individual donor pass, available in multiples
> 3) city pass — this will be applicable only for individual only."

**Decided.** Two levels, not one flat list.

**Product** — the shape of the thing, fixed by the platform:

| Product | Covers | People | Date | Time |
|---|---|---|---|---|
| Individual | one or more chosen pandals | 1 | per pandal | per pandal |
| Group | as Individual, bought in multiples | chosen at purchase | per pandal | per pandal |
| City | one or more chosen pandals | 1 — Individual only | one date | none |

**Category** — who the holder is, defined **by each pandal**, extensible: Sponsor, VIP,
Para Pass, Senior Citizen, Donor, and anything else that pandal wants. Category carries
the price. A Group Pass is a category bought in multiples with a chosen head count.

**Killed:** the document's flat list (General, Preview, VIP, Family, Group), and the
prototype's per-pandal *Family Pass / Sponsor Pass* toggle as a third parallel taxonomy.

**Note.** *Sponsor* being a category is what connects the sponsorship hierarchy to the
pass catalogue: passes issued out of a sponsor's pool are issued in that category.

## D5 · Gates work offline — *answers the standing question, and reopens C7*

> "It shud work offline."

**Decided.** A gate admits and refuses without connectivity, and reconciles when it
returns.

**This collides with D1, and the collision is the most important thing on this page.**
There are two separate connectivity questions and D1 only answers one of them:

| | If it is offline |
|---|---|
| **The gate device** | Solved: it verifies the code's authenticity locally and syncs admissions later. |
| **The visitor's phone** | *Not solved.* If the server mints the code, the visitor needs signal — standing in a crowd of fifty thousand on Ashtami night, which is exactly where mobile data does not work. |

A server-minted code makes the visitor's connectivity a hard dependency of entry. The fix
is to move minting off the server: at purchase the phone is given a secret for each pandal
on the pass, and generates a time-based code from it with no network at all. The gate
verifies that code offline against the same pandal's key, records the admission locally,
dedupes locally, and syncs later. Authenticity is offline; consumption stays
server-authoritative and reconciles.

Residual risk to accept or design away: during an outage, two gates at one pandal could
each admit the same code once. Either the gates at a pandal peer over a local network, or
we accept it and catch it in reconciliation.

**Still open:** whether manual-exception admission (C7) is still wanted as well. The
answer above may have been meant as *"offline is the answer to the dead-phone problem,
so no override is needed"*, or the two may be separate. See Q6.

## D6 · A sponsor's pool is per pandal — *resolves C8*

> "One sponsor can receive passes from 5 different pandals. So they would need to manage this from the console."

**Decided.** A pool belongs to a (sponsor, pandal) pair. A sponsor holding packages at
five pandals holds five pools, and the console shows them separately and as a rollup.
The single aggregate "735 remaining" in the mockup is a rollup, not a balance.

Sub-sponsor pools inherit the same shape: a sub-sponsor buys from its parent's pool **at
one pandal**, so its own pool is per pandal too.

**Consequence.** The invariant to enforce is per pandal at every tier: the sum of a
sponsor's outstanding and issued passes at a pandal never exceeds what that pandal
allocated it, and the same one level down.

## D7 · Credentials are never displayed — *resolves C9*

**Decided by us, at the client's direction ("you can fix").** Third-party administrator
accounts are created by invitation. The invitee sets their own secret. No screen, table,
export or log ever shows it. The mockup's sub-sponsor password column is not built.

---

## D8 · Branding entitlement is enforced at upload — *resolves C10*

**Decided by us, at the client's direction.** A sponsor cannot create more live placements
than its package grants. Attempting to exceed the entitlement is refused at upload with a
clear message, rather than accepted and caught later. The mockup's "2 placements · 3 in
use" state is not reachable.

---

## D9 · Screens are named for what they show — *resolves C11*

**Decided by us, at the client's direction.** The Super Admin's *Groups* screen becomes
**Pandals**, because it is a pandal master. *Donations* becomes **Revenue**, because it
reports passes, services and donations together. Names are fixed before they reach routes,
endpoints and permissions.

## D10 · Sign-up is mobile and OTP; the profile comes after — *resolves C12*

> "Sign up is with mobile number and OTP. Then we ask them to fill their profile, that's where we take First Name, Last Name, EmailID, DoB."

**Decided.** Identity is the mobile number. Email is profile data, never a sign-in
credential. Sign-up captures the number and nothing else; the profile screen then captures
**first name, last name, email and date of birth** — the last two of which no earlier
source mentioned.

**Consequence.** Date of birth is new, and it is useful: the eligibility questionnaire's
second question is *"Age group confirmed"*, which date of birth answers directly rather
than by asking again.

**Consequence.** Full name splits into first and last. The prototype's single *Full Name*
field is superseded.

---

## D11 · Administrators sign in with mobile and OTP

> "For admin panel too if it's possible, login with Phone and OTP. It's easier. If not possible then Username and Password."

**Decided.** It is possible, and it is the same mechanism the visitor app already needs, so
it costs nothing extra.

**One caveat, with a recommendation.** Phone plus OTP is a single factor — possession of a
SIM. For a Pandal Admin, a Sponsor Admin or a Sub-Sponsor Admin that is proportionate. For
a **Super Admin**, who can see every payment and every visitor on the platform, a SIM swap
would be enough to take the platform. Recommended: phone and OTP for the three scoped
roles, and password **plus** OTP for Super Admin only. Cheap, and it removes the worst case.

## D12 · A subdomain per pandal

> "Subdomain per pandal."

**Decided.** `ballygunge-cultural.edurgapuja.app`. The web tier resolves the
pandal from the `Host` header; the slug and the subdomain are the same string.

**What it costs.** One wildcard DNS record and one wildcard certificate for
`*.edurgapuja.app`. No per-pandal DNS, no per-pandal certificate, no per-pandal
deployment. Onboarding a committee stays a database insert.

**What it forces.**

- **Reserved names must be blocked.** `www`, `api`, `admin`, `app`, `mail`,
  `static`, `assets`, `staging` and their kin. A committee that legitimately
  wants to be called *app* takes `app-pandal` or similar.
- **DNS constrains the name**: lowercase, letters, digits and hyphens, no leading
  or trailing hyphen, 63 characters at most.
- **The name is effectively permanent.** It will be on a banner, in WhatsApp
  forwards and possibly in print. Changing it keeps the old one as a 301 forever,
  so `pandal_domain_alias` exists from day one.
- **Cookies become a security question, not a configuration detail.** A cookie
  scoped to `.edurgapuja.app` is sent to *every* pandal subdomain — including
  pages whose content pandal admins control. The admin session is therefore
  **host-only** on `admin.edurgapuja.app`, with no `Domain` attribute, and a
  checkout token never outlives the origin that created it.
- **No shared sign-in across pandal sites in v1.** A visitor who donated at one
  pandal is an unfamiliar visitor at the next. That is a little friction and a lot
  less risk, and identity persists in the app where it belongs.

**Two things it makes easy later.** Search engines treat subdomains as
near-separate sites, so each committee's page accrues its own authority for its
own name — which is what a committee actually wants. And a custom domain becomes
a column plus on-demand certificate issuance rather than a rearchitecture.
